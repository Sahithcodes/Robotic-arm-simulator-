# Pick and place diagnosis

## 1. Arm geometry and coordinate frame

- The arm is a six revolute joint PUMA-style chain using standard DH transforms, `Rz(theta) * Tz(d) * Tx(a) * Rx(alpha)` ([src/robot/robotConfig.ts:37-40](../src/robot/robotConfig.ts), [src/robotics/dh.ts:5-17](../src/robotics/dh.ts)). Link dimensions are `d1=0.70 m`, `l2=0.43 m`, `l3=0.37 m`, `d4=d5=0`, `d6=0.10 m`; limits are J1 [-170,170], J2 [-225,45], J3 [-216,90], J4 [-110,170], J5 [-100,100], J6 [-266,266] degrees ([src/robot/robotConfig.ts:9-32](../src/robot/robotConfig.ts)). Internal angles are radians; UI joint sliders display degrees ([src/components/JointControls/JointSliderPanel.tsx:21-40](../src/components/JointControls/JointSliderPanel.tsx)). Length units are meters ([src/types/robotics.ts:14-19](../src/types/robotics.ts)).
- Three.js uses Z as up: camera up is `[0,0,1]`, the table plane is XY, and the table top is `z=0.78 m` ([src/components/RobotViewer/CanvasContainer.tsx:62-64](../src/components/RobotViewer/CanvasContainer.tsx), [src/components/RobotViewer/Scene.tsx:146-148, 236-250](../src/components/RobotViewer/Scene.tsx)). The arm DH base is at world `(0,0,0.28)` and the first DH offset raises the shoulder to `0.98 m` ([src/robot/robotConfig.ts:34-35, 41-52](../src/robot/robotConfig.ts), [src/robotics/forwardKinematics.ts:24-28](../src/robotics/forwardKinematics.ts)).
- The table is `1.15 x 0.90 m`, centered at `(0.80,-0.08)`, top at `0.78 m`, thickness `0.045 m` ([src/robotics/task5.ts:81-87](../src/robotics/task5.ts)). The pedestal comment says it clears the tabletop, but the visual pedestal/base is centered at world origin, while the DH mounting origin is at z=0.28 and there is no visible pedestal mesh connecting them ([src/robot/robotConfig.ts:34-35](../src/robot/robotConfig.ts), [src/components/RobotViewer/RobotKinematicChain.tsx:69-83](../src/components/RobotViewer/RobotKinematicChain.tsx)). This leaves the intended physical base/mount geometry uncertain.

## 2. End effector and TCP

- End-effector pose is computed by DH forward kinematics, then used directly to place the rendered end-effector group. It is not queried with `getWorldPosition` ([src/robotics/forwardKinematics.ts:13-55](../src/robotics/forwardKinematics.ts), [src/components/RobotViewer/RobotKinematicChain.tsx:104-110, 204-229](../src/components/RobotViewer/RobotKinematicChain.tsx)).
- There is no separately modeled TCP node. The FK endpoint `T06` is the rendered gripper mount; a book contact point is represented by local offset `(0,0,-0.085) m` ([src/robotics/task5.ts:94-100](../src/robotics/task5.ts), [src/components/RobotViewer/RobotKinematicChain.tsx:213-229](../src/components/RobotViewer/RobotKinematicChain.tsx)). The 0.10 m `d6` flange offset plus the additional -0.085 m gripper offset means the actual contact point is only 0.015 m from the wrist flange along local Z. Whether this matches the intended tool geometry is not established by the Live Script source available in the project.

## 3. How tasks move the arm

- The predefined task uses fixed Cartesian P1-P4 waypoints with fixed orientations. A numerical inverse-kinematics solver generates joint waypoints; the trajectory then interpolates those joint angles ([src/robotics/task5.ts:53-74, 108-168](../src/robotics/task5.ts), [src/store/simulationStore.ts:416-423](../src/store/simulationStore.ts)).
- Autonomous pick also runs IK for a list of hard-coded *relative* stages (pre-grasp, grasp, lift, drop approach, drop, home). Its pickup XY is passed into the planner from the current store object, rather than fixed inside the planner ([src/robotics/autonomousPlanner.ts:87-105](../src/robotics/autonomousPlanner.ts), [src/store/simulationStore.ts:157-174](../src/store/simulationStore.ts)). However, its TCP target position is derived using a constant gripper offset and ignores the book yaw.

## 4. Object storage and planning input

- Zustand stores the book as `simulatedObject`, including world position, rotation, dimensions, attach flags, and reachability; a duplicate `bookPosition` field also remains ([src/store/simulationStore.ts:44-57, 128-135](../src/store/simulationStore.ts)). The Scene renders and drags the Zustand object position, clamping it to table bounds ([src/components/RobotViewer/Scene.tsx:121-149](../src/components/RobotViewer/Scene.tsx)).
- Planner creation reads `simulatedObject.position` at the moment plan is requested ([src/store/simulationStore.ts:166-174](../src/store/simulationStore.ts)). The initial book position and drop target are constants in `task5.ts` / `autonomousPlanner.ts` ([src/robotics/task5.ts:89-92](../src/robotics/task5.ts), [src/robotics/autonomousPlanner.ts:15](../src/robotics/autonomousPlanner.ts)); the autonomous planner does not use the initial pickup coordinate as the live pickup target.

## 5. Grasp and attachment behavior

- The object is not re-parented in the Three.js scene. On a successful grasp check, the store computes a local offset and marks it attached; each animation tick recomputes the object world position from FK and that offset ([src/store/simulationStore.ts:318-347, 399-412](../src/store/simulationStore.ts)). This is kinematic following, not a scene-graph attachment.
- At the grasp waypoint, the code checks distance from the gripper's transformed local contact point to the object center. If it exceeds `0.035 m`, execution stops with an error ([src/store/simulationStore.ts:318-324](../src/store/simulationStore.ts)). The gripper closes only after this check succeeds ([src/store/simulationStore.ts:335-345](../src/store/simulationStore.ts)). The rendered opening changes between `0.13 m` and `0.092 m` ([src/components/RobotViewer/RobotKinematicChain.tsx:209-229](../src/components/RobotViewer/RobotKinematicChain.tsx), [src/robotics/task5.ts:94-100](../src/robotics/task5.ts)).

## 6. Root causes, ranked by likelihood

1. **Tool/TCP geometry is internally inconsistent or insufficiently defined.** `T06` is rendered as the gripper mount, but the planner targets that frame using a fixed -0.085 m contact offset; target conversion and tool orientation are not derived from one explicit TCP definition. The planner computes grasp as `object.z - offset.z`, which places the flange above the book, but the target yaw/orientation is always `(0,0,0)` and does not account for object yaw ([src/robotics/autonomousPlanner.ts:95-100,125-131](../src/robotics/autonomousPlanner.ts), [src/robotics/task5.ts:94-100](../src/robotics/task5.ts)).
2. **The tool orientation check is not the intended downward-grasp constraint.** The planner compares the end-effector rotation matrix to identity and accepts only a small rotation from identity ([src/robotics/autonomousPlanner.ts:18-22](../src/robotics/autonomousPlanner.ts)); identity has local +Z pointing upward in this Z-up scene, whereas the fingers extend toward local -Z. This can reject valid top-down solutions or select a pose with an incorrect finger direction.
3. **Close-clearance/table collision logic is inconsistent with the intended contact.** The collision routine calculates the finger bottom as endpoint Z plus the negative offset minus half finger length ([src/robotics/autonomousPlanner.ts:52-53](../src/robotics/autonomousPlanner.ts)); the finger boxes are centered at the offset and extend along local Z, while the planner permits only a 1 cm table penetration allowance and does not model finger orientation in that calculation. It can therefore falsely reject the final descent or approve unsafe orientations.
4. **IK silently clamps candidate angles, while returned status can only say convergence, not explain clamping or limits.** The solver clamps every update and reports `converged=false` only when it exhausts iterations ([src/robotics/inverseKinematics.ts:94-99, 138-188](../src/robotics/inverseKinematics.ts)). The planner does check convergence and residual before accepting a pose, so this is less likely than TCP/orientation mismatch but can make edge positions fail as a generic workspace error.
5. **The predefined path cannot follow a moved book.** Predefined Cartesian waypoints are fixed, including P3 `(0.32,-0.10,0.90)` ([src/robotics/task5.ts:53-74](../src/robotics/task5.ts)); this explains failure when using the predefined mode after moving the book, but not a correctly replanned autonomous task.
6. **The geometry source is ambiguous.** `robproject.mlx.zip` contains a MATLAB Live Script package with `document.xml` and `output.xml`, but no MATLAB code file; the actual source cell definitions/parameters cannot be confirmed from the project artifact. The TypeScript DH dimensions appear to cite a separate paper instead ([src/robot/robotConfig.ts:4-16](../src/robot/robotConfig.ts)). The DH transform and rendered chain share FK, so a local/world mismatch between those two is not the leading cause.
